# 0006. Репозиторий-агрегат и команды движка вместо use case'ов

Статус: принято · 2026-11-02

## Контекст
ТЗ §7 рисует цепочку `UI → ViewModel → UseCase → Repository`, задача на архитектуру просила отдельный `LedgerRepository`. CLAUDE.md и роль архитектора требуют минимум абстракций: не вводить слой, который не нужен двум потребителям. Каждое действие банкира должно писаться одной транзакцией (ТЗ §9): «новый игрок + закуп», «выход + расчёт», «рейк отдан + закрыть игру», «приём передачи = игра + игроки + журнал + акт».

## Решение
- Команды движка (`Commands`, `Handovers`, `Imports` в `:core:domain`) — чистые функции `снимок → GameChange`. `GameChange` = upsert строки игры и игроков + INSERT записей журнала и актов.
- Один `GameRepository` на агрегат «игра»: `observe…`/`get…` возвращают `GameSnapshot`, запись — только `commit(List<GameChange>)` одной транзакцией. Обновить или удалить запись журнала нельзя, потому что такого метода нет; удаляются только игры целиком, каскадом.
- Плюс `PlayerNameRepository` (подсказки, объединение имён), `SettingsRepository` (DataStore), `BackupRepository` (импорт множества игр в одной транзакции нельзя собрать из ViewModel).
- Use case'ов нет. ViewModel: `snapshot` из Flow → `Commands.x(snapshot, …, Stamp.now(clock))` → `repository.commit(change)`. Общие сценарии двух фич (погашение долга с экрана долгов и из предупреждения при посадке) — это те же три строки, отдельного класса не заводим.
- История, статистика и долги считаются в памяти из `observeAllGames()`. Запросы-оптимизации — только после замера на реальном объёме.

## Альтернативы
- `LedgerRepository` + `GameRepository` + `PlayerRepository`: транзакцию «игрок + закуп» пришлось бы собирать поверх трёх интерфейсов (TransactionRunner или use case) — лишний слой.
- Use case на каждую операцию: тонкие обёртки «вызови движок, сохрани», которые ничего не проверяют сверх движка.

## Последствия
- Отклонение от ТЗ §7 по слоям — осознанное; если у сценария появится второй потребитель с собственной логикой, use case заводится точечно.
- Data-layer реализует `commit` как одну Room-транзакцию с проверками (`seq` продолжает журнал, активных игр ≤ 1) и сам обновляет справочник имён.
- Тесты команд не нуждаются ни в моках, ни в корутинах.
