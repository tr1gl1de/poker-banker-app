# 0005. Представление журнала: чаевые, отмена, проценты, деньги

Статус: принято · 2026-11-02 · полный контракт — `docs/plan/m1-domain.md`

## Контекст
ТЗ §8 задаёт поля `LedgerEntry` и десять типов записей, но не говорит, как записать чаевые игроку за столом (фишки переходят из рук в руки), доход, который старый банкир забирает при передаче, и что именно отменяет «Отменено». Нужно, чтобы касса и фишки сходились в любом сценарии: выход и возврат, чаевые, банкир-игрок, частичная оплата, долг и его погашение в другой игре, прощение, отмена любой операции, передача посреди игры.

## Решение
1. **Деньги — `Long` рубли, без value class.** 1 фишка = 1 ₽, поэтому отдельные типы «фишки»/«рубли» ничего не ловят, а value class мешает арифметике, Room и сериализации. Защита — валидация (`0..Money.MAX_AMOUNT = 1e8`) и тесты. Id — `@JvmInline value class` над `kotlin.uuid.Uuid` (их легко перепутать, а арифметики над ними нет).
2. **Проценты — целые 0..100**, `round(amount·p/100)` половина вверх: `(amount·p + 50) / 100` (CLAUDE.md, правило 1). При `amount ≤ 1e8` переполнения нет. Дробные проценты (2,5 %) — будущий ADR с повышением `Game.schemaVersion`.
3. **Знак не хранится**: все `amount > 0` (`CASH_OUT ≥ 0`), направление задаёт тип. `outstanding = W + paid + forgiven − charged − paidOut` (> 0 банкир должен, < 0 игрок должен) по всему журналу игрока в игре.
4. **Чаевые — два типа.** `TIP` — рублями: банкиру (`counterparty = null`, в доход) или вышедшему игроку (к его W). `TIP_CHIPS` — **новый тип**: игроку за столом; фишки не возвращаются в банк, денег не двигают. `CASH_OUT.amount` = F целиком. Сдано в банк = `Σ CASH_OUT − Σ TIP_CHIPS`, поэтому сверка «выдано = сдано» верна (с одним типом получатель сдал бы те же 100 фишек второй раз). Тип выбирает движок по статусу получателя в момент выхода.
5. **`INCOME_TAKEN` — новый тип**: старый банкир забирает доход наличными из кассы при передаче. Без записи касса нового банкира по журналу больше его наличных. Забрать можно не больше `min(доход, касса − рейк к отдаче)` — рейк заведения в карман не уходит.
6. **Операции.** Все записи одного действия делят `operationId`; порядок задаёт `seq` (1..n без пропусков). Выход — две операции в одной транзакции: «Выход» (CASH_OUT + чаевые) и «Расчёт» (PAYMENT/PAYOUT), чтобы отменить ошибочный подсчёт фишек, не «вернув» в журнале реально выданные деньги.
7. **Отмена** — `REVERSAL` на каждую действующую запись операции, с необязательной причиной. Отменённые и отменяющие записи исключаются из всех сумм. Отмена отмены запрещена (ошибку исправляют, повторив операцию), повторная — тоже, `INCOME_TAKEN` не отменяется. В CLOSED можно отменять только погашения, выплаты и прощения; остальное — через «Переоткрыть».
8. **Статус игрока, первый закуп, время расчёта — производные журнала**, не поля `Player` (ТЗ §8 их перечисляет): так отмена и передача не дают рассинхрона. `Player` = id, gameId, name, joinedAt.
9. **`Game.bankerPlayerId` вместо `bankerIsPlayer` + `Player.isBanker`**: один источник, после передачи указывает на нового банкира (сбор с бывшего банкира в режиме «с каждого» снова берётся).
10. **Передача — отдельная сущность `Handover`** (ТЗ §8), а не тип записи: денег она не двигает (деньги — `INCOME_TAKEN`). Экран журнала вставляет строку «Игра принята от …» по времени. Ранний выход — флаг `earlyExit` у `CASH_OUT`; «изменено после закрытия» — `Game.editedAfterClose`.
11. Погашение старого долга — `PAYMENT` в **старую** игру (ТЗ §3.7), `bankerName` — кто принял деньги. Прощение — `DEBT_FORGIVEN`, уменьшает доход банкира этой записи.

## Альтернативы
- `CASH_OUT = F − чаевые фишками` и один тип `TIP`: сверка без поправки, но отмена такой записи чаевых не меняла бы сданные фишки — смысл записи зависел бы от соседних.
- Тип записи под передачу или ранний выход: лишняя ветка во всех суммах ради записи без денег.
- Базисные пункты для процентов: на будущее гибче, но расходится с правилом CLAUDE.md и усложняет ввод; ТЗ оперирует целыми процентами.
- Хранить статус игрока: быстрее запросы, но второй источник правды.

## Последствия
- Тождество `касса = (рейк к отдаче + доход − забрано) + фишки в игре + долг банкира − долги игроков` верно для любого журнала и проверяется property-тестами.
- В `EntryType` два типа сверх ТЗ §8 (`TIP_CHIPS`, `INCOME_TAKEN`); в `LedgerEntry` поля `seq`, `operationId`, `earlyExit`. Data-layer хранит их колонками, пакет передачи — полями.
